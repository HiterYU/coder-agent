# LeetCode 编程训练 Agent 总体框架

## 1. 项目目标

构建一个面向程序员的 Code 能力训练 Agent，基于 LeetCode 题目进行长期练习陪伴。Agent 不只是给题目和答案，而是根据用户的解题过程进行观察、提示、复盘和个性化建模，帮助用户发现自己的薄弱点，并在未来可能犯错时提前提醒。

核心目标：

1. 获取并组织 LeetCode 题目、题解、标签、难度和相关知识点。
2. 支持用户独立解题，在长时间卡住时提供分级提示，而不是直接给答案。
3. 根据用户提交的代码、思路、错误记录和求助行为生成个人能力画像。
4. 识别用户常见错误模式，在未来类似场景中主动给出预警。
5. 形成长期训练闭环：选题、做题、提示、提交、复盘、画像更新。

## 2. 用户使用流程

### 2.1 初始阶段

1. 用户选择训练目标：
   - 算法基础
   - 面试刷题
   - 某类专题，例如动态规划、二叉树、图论、滑动窗口
   - 某家公司高频题
2. Agent 评估用户当前水平：
   - 已做题数量
   - 熟悉语言
   - 自评薄弱方向
   - 简单诊断题
3. Agent 生成初始训练计划。

### 2.2 单题训练流程

1. Agent 给出题目描述、输入输出、约束和示例。
2. 用户开始解题，可以输入：
   - 解题思路
   - 伪代码
   - 代码
   - 报错信息
   - 求提示请求
3. Agent 观察用户状态：
   - 停留时间
   - 是否多次修改同一段代码
   - 是否反复出现同类错误
   - 是否对题目关键约束理解错误
4. 当用户长时间未完成时，Agent 分级提示：
   - 第一级：提醒题目关键条件
   - 第二级：提示可能的数据结构或算法方向
   - 第三级：提示核心转移关系、双指针移动规则等
   - 第四级：给出接近完整的解题框架
   - 最后：给标准答案和详细解释
5. 用户提交答案后，Agent 进行评估：
   - 正确性
   - 时间复杂度
   - 空间复杂度
   - 代码风格
   - 边界条件覆盖
   - 是否有更优解法
6. Agent 生成复盘并更新用户画像。

## 3. 核心模块设计

### 3.1 题目数据模块

负责获取、整理和结构化 LeetCode 题目。

数据内容：

- 题目 ID
- 标题
- 难度
- 标签
- 题目描述
- 示例
- 约束条件
- 官方题解或高质量题解
- 多语言参考答案
- 常见错误点
- 相似题目

实现方式：

- 初期可以手动整理一批高频题作为 MVP 数据集。
- 后续再接入公开数据源或自建题库管理后台。
- 题目应被结构化存储，方便 Agent 检索、筛选和展示。

### 3.2 解题会话模块

负责管理用户当前正在做的题目和上下文。

需要记录：

- 当前题目
- 用户使用语言
- 开始时间
- 用户历史输入
- 已经给过哪些提示
- 用户当前代码版本
- 编译或运行结果
- 错误信息
- 当前卡点判断

核心能力：

- 判断用户是否真正卡住。
- 避免重复给相同提示。
- 控制提示强度，优先引导而不是直接给答案。
- 保留会话上下文，方便复盘。

### 3.3 提示策略模块

这是 Agent 的关键差异化能力。

提示原则：

1. 不直接泄露答案，除非用户明确要求或已经多次失败。
2. 根据用户当前阶段给提示：
   - 题意理解阶段
   - 思路选择阶段
   - 代码实现阶段
   - Debug 阶段
   - 复杂度优化阶段
3. 根据用户历史弱点个性化提示。

提示分级：

| 等级 | 目标 | 示例 |
|---|---|---|
| Level 1 | 轻提示 | “注意输入数组可能为空吗？” |
| Level 2 | 方向提示 | “这题可以考虑用双指针维护一个窗口。” |
| Level 3 | 关键思路 | “窗口右边界扩张，左边界在不满足条件时收缩。” |
| Level 4 | 代码骨架 | 给出主要循环结构和变量含义 |
| Level 5 | 完整题解 | 给出答案、复杂度和复盘 |

### 3.4 代码评估模块

负责分析用户答案。

评估维度：

- 是否符合题意
- 是否通过样例
- 是否覆盖边界条件
- 时间复杂度是否可接受
- 空间复杂度是否可接受
- 是否存在常见 bug
- 变量命名和结构是否清晰

可选能力：

- 沙箱运行用户代码。
- 生成测试用例。
- 对比标准答案。
- 识别错误类型，例如：
  - 下标越界
  - 忘记初始化
  - 循环条件错误
  - 边界条件漏判
  - 状态转移写错
  - 递归终止条件错误
  - 贪心证明不充分

### 3.5 用户画像模块

负责长期记录用户能力和偏好。

画像内容：

- 熟悉语言
- 常做题型
- 擅长题型
- 薄弱题型
- 常见错误模式
- 解题速度
- 提示依赖程度
- 是否容易忽略边界条件
- 是否偏向暴力解法
- 是否不擅长复杂度分析
- 是否在某类题型上反复卡住

示例画像：

```json
{
  "language": "Python",
  "strengths": ["哈希表", "数组遍历"],
  "weaknesses": ["动态规划状态定义", "二叉树递归边界"],
  "common_mistakes": [
    "忘记处理空数组",
    "滑动窗口左边界更新不及时",
    "DP 初始化不完整"
  ],
  "hint_preference": "先给方向，不要直接给代码",
  "risk_patterns": [
    {
      "topic": "sliding_window",
      "risk": "窗口收缩条件容易写反"
    }
  ]
}
```

### 3.6 错误预测模块

根据用户历史画像和当前题目特征，预测用户可能犯错的地方。

输入：

- 当前题目标签
- 当前题目难度
- 当前代码片段
- 用户历史错误
- 用户当前解题阶段

输出：

- 风险点
- 是否需要主动提示
- 提示内容
- 提示强度

示例：

用户历史上多次在滑动窗口题中写错收缩条件。当当前题目是滑动窗口，并且用户写出类似 `while count > k` 的逻辑时，Agent 可以提示：

> 你之前在这类题里容易把窗口收缩条件写反。这里建议重新确认一下：什么时候窗口是不合法的？左边界应该在什么条件下移动？

### 3.7 题目筛选模块

根据题目标签、难度、完成状态和用户当前训练目标筛选题目。

筛选策略：

1. 支持按 topic、难度和关键词过滤。
2. 展示完成状态，避免用户重复进入已完成题。
3. 在复盘中记录薄弱 topic，供用户选择后续训练题。
4. 保持逻辑简单可解释，不在 MVP 阶段保留独立推荐链路。

## 5. MVP 范围

第一版不要做得太大，建议先验证核心闭环。

### 5.1 MVP 必做功能

1. 手动整理 30-50 道 LeetCode 高频题。
2. 支持用户选择题目或按标签筛选题目。
3. 支持单题对话式解题。
4. 支持分级提示。
5. 支持用户提交代码后生成复盘。
6. 支持记录用户常见错误。
7. 支持根据错误生成简单个人画像。
8. 支持按标签、难度和完成状态继续选择训练题。

### 5.2 MVP 暂不做功能

1. 不必一开始接入完整 LeetCode 题库。
2. 不必一开始做复杂代码沙箱。
3. 不必一开始做多人系统。
4. 不必一开始做完整前端，可以先用 CLI 或简单 Web 页面。
5. 不必一开始做非常复杂的机器学习模型，先用规则和 LLM 总结即可。

## 6. 技术路线建议

### 6.1 后端

推荐：Python + FastAPI

原因：

- 适合快速构建 API。
- 方便做代码分析、数据处理和 Agent 编排。
- 生态成熟。

核心 API：

- `GET /problems`
- `GET /problems/{id}`
- `POST /sessions`
- `POST /sessions/{id}/message`
- `POST /sessions/{id}/submit`
- `GET /users/{id}/profile`

### 6.2 数据库

MVP 推荐：SQLite 或 PostgreSQL

主要表：

- `problems`
- `solutions`
- `sessions`
- `messages`
- `submissions`
- `user_profiles`
- `mistake_patterns`

### 6.3 Agent 层

可以把 Agent 拆成几个子 Agent 或工具：

1. Problem Agent：负责题目解释和知识点拆解。
2. Hint Agent：负责分级提示。
3. Review Agent：负责代码审查和复杂度分析。
4. Profile Agent：负责总结用户画像。

MVP 阶段可以先由一个 Orchestrator 调用不同 prompt 模板实现，不需要过早拆成复杂多 Agent 系统。

### 6.4 前端

MVP 可选方案：

1. CLI：最快实现，适合内部验证。
2. Streamlit：适合快速做交互原型。
3. Next.js：适合之后产品化。

建议第一阶段用 Streamlit 或简单 Web UI，降低前端成本。

## 7. 两人分工建议

假设两个人分别负责 Agent/算法侧和产品/工程侧。

### 成员 A：Agent 与算法训练负责人

主要负责智能能力和训练逻辑。

职责：

1. 设计题目结构化格式。
2. 整理首批 30-50 道题目。
3. 设计分级提示策略。
4. 设计代码复盘 prompt。
5. 设计用户画像 schema。
6. 设计错误模式分类体系。
7. 实现 Hint Agent、Review Agent、Profile Agent 的核心逻辑。
8. 设计题目筛选和训练记录规则。

交付物：

- 题目数据 JSON/数据库表结构
- 分级提示 prompt
- 代码复盘 prompt
- 用户画像 schema
- 错误模式 taxonomy
- 题目筛选策略文档或代码
- Agent 核心调用逻辑

### 成员 B：后端、前端与系统集成负责人

主要负责产品可用性和工程落地。

职责：

1. 搭建后端服务。
2. 设计 API。
3. 实现会话管理。
4. 实现题目读取、提交记录、用户画像存储。
5. 搭建简单前端或 CLI。
6. 接入 LLM API。
7. 实现基础登录或用户 ID 区分。
8. 部署 MVP。

交付物：

- FastAPI 后端
- 数据库 schema 和迁移脚本
- CLI 或 Web UI
- 会话系统
- 用户数据存储
- LLM 调用封装
- 部署脚本或运行文档

## 8. 两人协作边界

### A 负责“Agent 是否聪明”

关注问题：

- 提示是否合适？
- 是否过早泄露答案？
- 是否能识别用户卡点？
- 是否能总结个人弱点？
- 是否能基于行为证据更新画像？

### B 负责“系统是否可用”

关注问题：

- 用户能否顺利开始做题？
- 会话是否稳定？
- 数据是否正确存储？
- API 是否清晰？
- 前端交互是否顺畅？
- 系统是否方便部署和调试？

### 共同负责

以下部分需要两人一起定：

1. 用户完整体验流程。
2. 题目数据格式。
3. 用户画像字段。
4. 提示等级定义。
5. MVP 验收标准。

## 9. 题目筛选开发阶段

### 第一阶段：原型验证，1-2 周

目标：跑通单题训练闭环。

任务：

- 整理 10 道题。
- 实现命令行或简单页面。
- 支持用户看题、输入思路、请求提示、提交代码。
- Agent 能给分级提示和复盘。
- 手动保存用户画像。

验收标准：

- 一个用户可以完整做完一道题。
- Agent 不直接剧透答案。
- Agent 能指出至少 2 类错误。
- 做完题后能生成复盘。

### 第二阶段：MVP，3-4 周

目标：形成可连续训练的产品。

任务：

- 扩展到 30-50 道题。
- 增加用户画像存储。
- 增加题目筛选。
- 增加错误模式统计。
- 增加更稳定的 UI。

验收标准：

- 用户可以连续训练多道题。
- 系统能记录用户历史。
- 系统能发现用户高频错误。
- 系统能按标签、难度和完成状态筛题。

### 第三阶段：增强版，4 周以上

目标：提升智能化和产品体验。

任务：

- 接入代码运行沙箱。
- 自动生成测试用例。
- 更精细的错误预测。
- 做知识点图谱。
- 支持复习计划。
- 支持面试模拟模式。

## 11. 关键产品原则

1. 训练优先，不是答案搜索器。
2. 提示要递进，不要一次性给完整答案。
3. 用户画像要来自行为证据，不要凭一次表现下结论。
4. 错误预测要克制，避免频繁打断用户。
5. 复盘要具体，指出这道题里发生了什么。
6. 题目筛选要有理由，让用户知道为什么看这题。
7. MVP 先证明闭环，再追求完整题库和复杂能力。

## 12. 最小可行版本总结

最小版本可以这样定义：

- 30 道精选 LeetCode 题。
- 一个简单 Web UI 或 CLI。
- 用户能做题、求提示、提交代码。
- Agent 能分级提示。
- Agent 能复盘代码和思路。
- 系统能记录用户常见错误。
- 系统能按标签、难度和完成状态筛选训练题。

两人分工：

- 成员 A 做 Agent 智能逻辑、题目数据、提示和画像。
- 成员 B 做后端、前端、数据库、会话和部署。

优先把“做一道题后的个性化复盘和题目筛选”做扎实，这是这个产品区别于普通 LeetCode 题解工具的核心价值。
